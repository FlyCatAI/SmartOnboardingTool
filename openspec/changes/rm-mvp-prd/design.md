## Context

**业务背景**：联合收单业务客户经理（首批 200 人，1 支行灰度 2 周）目前以 PC + 纸质方式展业，存在「信息不在线 / 任务流转无闭环 / 现场展业效率低」三大痛点。本次 MVP 在 4-6 周内交付一款轻量级小程序，覆盖工作台、商户管理、任务管理三大模块，验证移动展业产品形态。

**当前状态**：行内已有 SSO、商户主数据系统、收单交易系统、消息推送通道、文件存储服务等基础能力（提案 Impact 章节已列依赖）。本期为全新小程序，无遗留代码。

**关键约束**：
- 工期 4-6 周（MVP），上线后 2 周灰度。
- 终端形态为小程序（订阅消息 + 站内通知双通道）。
- 数据合规：商户敏感字段脱敏 + OTP 二次校验解密 + 全量操作日志保留 ≥ 6 个月。
- 行内统一身份认证体系，不允许自建账号密码。
- 一个客户经理 ↔ 一个所属支行 ↔ 一个团队（一级主管），v1 不考虑跨团队 / 跨支行。

**主要干系人**：业务方（联合收单业务部）、客户经理、团队主管、行内安全合规、SSO / 商户主数据 / 收单系统接口方、运营培训团队。

## Goals / Non-Goals

**Goals：**

1. 在 MVP 周期内交付可被一线客户经理日常使用的小程序，闭环「工作台 + 商户管理 + 任务管理 + 通知」四类核心场景。
2. 任务全生命周期可在线追踪，状态机（七态）与通知触发场景在产品 / 数据 / 接口三层语义一致。
3. 商户档案与收单 / 交易数据移动端可见，敏感字段在合规要求下可调阅明文。
4. 形成可复用的客户经理身份、权限、操作日志与通知基础能力，为 v1.1+ 演进（电签、营销、绩效详情）打底。
5. 灰度试点期间形成可量化的关键指标基线（首屏性能、任务流转时长、跟进及时率、通知到达率），支撑放量决策。

**Non-Goals：**

1. 不做商户新增受理 / 入网申请、合同电子签、营销活动、绩效详情、跨支行任务调度（提案已划入 v1.1+）。
2. 不替代 PC 端原有展业系统，PC 与小程序在 MVP 阶段并存，能力差异化（小程序聚焦移动场景与展业现场）。
3. 不重建 SSO / 商户主数据 / 收单交易 / 推送任意一项后端能力，全部走调用，本期不接管它们的业务规则。
4. 不在 MVP 内提供「待确认任务超时自动确认」机制，仅做提醒，避免误判（已写入 task-management spec）。
5. 不做端上离线模式（弱网仅做友好提示与重试，不做本地写入队列）。

## Decisions

### Decision 1：任务状态机采用「七态显式 + 责任人字段」组合

**选择**：将「待派单 / 待认领 / 待处理 / 处理中 / 待确认 / 已完成 / 已关闭」七个状态作为正式状态机节点，配合「负责人 / 派单人」责任人字段表达派单链路与任务池链路。

**为什么**：
- 「待认领」与「待处理」责任人语义本质不同（无人 / 已分配），合并会让「我的任务」列表语义混乱。
- 「待确认」承载派单人确认动作，若降级为字段标签会让「已完成」含义双重化（声明完成 / 真实闭环），下游绩效统计与 SLA 计量出错。
- 银行风控合规场景下，独立状态比字段更便于权限控制、日志审计与 SLA 计量（GRA-10 已基于此决策修复并通过 PM 复审）。

**替代方案**：
- A. 保留五态 + 字段标签：被否，原因如上（GRA-10 复审记录在案）。
- B. 拆分更细的子状态（如「认领冲突待裁决」）：MVP 阶段过度设计，留给 v1.1+ 视实际数据再扩展。

### Decision 2：身份与权限走「行内 SSO + 端上轻量 RBAC」

**选择**：身份认证完全依赖行内 SSO（微信小程序通过行内 H5 桥接或行内自有授权页），权限模型固化为「客户经理 / 主管」两类角色 + 「自己 / 团队」两类数据范围，由后端在每个查询接口强制校验。

**为什么**：
- 行内合规与员工身份治理统一，自建账号体系会引发风险评审与运维负担。
- MVP 仅两类角色，复杂 ABAC 模型对当前业务无收益。
- 数据可见范围由后端强制校验，避免端上越权（spec merchant-management 已写入越权拒绝场景）。

**替代方案**：
- A. 端上做权限判断为主：被否，安全风险高，存在篡改可能。
- B. 引入完整 RBAC 框架（角色组 / 资源 / 动作矩阵）：MVP 体量不需要，v1.1+ 引入支行行长视角时再评估。

### Decision 3：通知双通道（订阅消息 + 站内）+ 通知-状态映射表强一致

**选择**：所有通知通过「行内推送（小程序订阅消息）+ 站内通知中心」两个通道下发，重要通知双通道，普通通知仅站内；触发场景与任务状态变化用映射表 1:1 描述（已写入 notification spec）。

**为什么**：
- 微信小程序订阅消息存在「一次授权一次下发」限制，单纯依赖订阅消息会漏通知；站内通知中心兜底保证可达性。
- 1:1 映射表是 GRA-10 修复的核心动作，确保产品 / 开发 / 测试三方对「什么状态触发什么通知给谁」无歧义。
- 免打扰开关（20:00-08:00 仅站内不推送）兼顾合规与用户体验。

**替代方案**：
- A. 仅订阅消息：被否，授权率与到达率不可控。
- B. 引入第三方 IM（企业微信）通道：MVP 不引入，v1.1+ 视员工渠道偏好评估。

### Decision 4：商户敏感字段「默认脱敏 + OTP 解密 30 秒 + 全量审计」

**选择**：商户证件号、银行卡号、手机号默认脱敏；点击「查看」走行内 OTP 二次校验，校验通过明文展示 30 秒后自动恢复；每次解密写入操作日志（操作人 / 时间 / 商户编号 / 字段名 / 设备指纹）。

**为什么**：
- 银行个人金融信息保护要求：明文需「按需调阅 + 二次校验 + 可追溯」三件套。
- 30 秒窗口 + 自动恢复脱敏，平衡现场展业效率与防截屏 / 防偷窥风险。
- 操作日志保留 ≥ 6 个月，满足审计回溯。

**替代方案**：
- A. 始终明文（仅角色控制）：被否，违反合规要求。
- B. 始终脱敏不可解密：被否，影响业务办理（如核对证件）。

### Decision 5：商户列表 / 任务列表 / 工作台首屏性能 SLA = 2 秒

**选择**：工作台首屏、商户列表首页、任务列表首页 P95 加载时长目标 ≤ 2 秒；商户搜索结果 ≤ 1 秒；收单状态实时数据延迟 ≤ 5 分钟。

**为什么**：
- 现场展业场景对响应速度敏感，>2 秒会显著降低使用意愿。
- 收单状态调用收单系统接口，5 分钟延迟为业务可接受上限（已写入 spec）。
- 列表分页 20 条 + 上滑加载，控制单次请求体积，兼顾弱网。

**替代方案**：
- A. 极致性能（≤ 1 秒）：MVP 不强求，避免引入复杂缓存 / 预加载机制。
- B. 不设 SLA：被否，无法在灰度阶段做客观评估。

### Decision 6：MVP 不做端上离线模式

**选择**：弱网 / 离线仅做友好提示与请求重试，不在端上做本地写入队列与数据同步。

**为什么**：
- 离线模式涉及冲突合并、加密本地存储、灰度回滚等复杂度，MVP 不在工期内。
- 客户经理展业场所多在商户门店 / 商业体，弱网概率可控；后续视试点反馈再评估。

### Decision 7：技术栈与发布策略由开发团队最终确定，本设计仅提产品约束

**选择**：本设计明确「响应时间 / 状态机语义 / 接口依赖 / 数据可见性 / 通知通道 / 合规要求」等产品约束；具体技术选型（前端框架、后端架构、数据库、缓存、灰度发布机制）由开发团队结合行内技术规范决定，不在本提案中强约束。

**为什么**：行内已有技术中台与发布规范，越界规定会与现有平台冲突；产品分析阶段聚焦「what / why」，「how」由后续 design / tasks 的工程团队补齐。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **下游接口口径未对齐**（SSO / 商户主数据 / 收单系统） | 阻塞开发联调，工期延后 | 启动设计阶段第一周完成 4 个下游系统的接口契约确认（字段、SLA、错误码），由开发团队与对应系统方对齐 |
| **小程序订阅消息授权率低** | 重要通知到达率不达预期 | 站内通知中心兜底；上线后监控授权率，授权率 < 60% 时考虑增加引导提示或评估企业微信通道 |
| **OTP 通道（短信 / 行内令牌）依赖外部** | 敏感字段查阅链路阻断 | 与安全合规 + 短信网关方提前确认通道与限流；准备人工兜底（联系支行行长授权）流程文档 |
| **七态状态机对业务方理解负担** | 客户经理 / 主管使用混淆，操作错误 | 配套 1 份「状态流转图」培训物料；任务详情页操作日志展示完整流转路径辅助理解 |
| **图片附件存储成本** | 跟进记录 9 张 × 5MB + 完成回报 6 张 × 5MB，存储与带宽成本增长 | 接入行内文件存储服务，使用 CDN；端上压缩到 ≤ 1MB 上传；保留期限策略由数据合规团队定 |
| **试点 200 人样本偏小** | MVP 数据不足以放量决策 | 灰度期定义关键指标基线（DAU / 任务流转时长 / 跟进及时率 / 通知到达率 / 客诉数）；主管视角增加「团队使用率」看板辅助评估 |
| **小程序版本审核与发布节奏** | 微信审核可能引入 1-3 天不可控延迟 | 在排期中预留审核 buffer；首次发布申请「企业内部小程序」减少审核环节 |
| **跨团队任务 / 商户调度需求被试点用户提出** | MVP 边界被推翻 | 提前与业务方对齐 v1.1+ 演进路线；试点期间收集需求但不本期实现 |

## Migration Plan

本期为新建小程序，无存量数据迁移，按以下节奏推进：

1. **第 1 周（设计阶段）**：完成 4 个下游接口契约确认、UI/UX 高保真稿、技术架构评审。
2. **第 2-4 周（开发阶段）**：分模块并行开发（工作台 / 商户 / 任务 / 通知 / 身份 5 条线），里程碑 = 各模块独立 demo 可演。
3. **第 5 周（联调与测试）**：四端联调（小程序前端 / 后端 / 下游接口 / 推送）、性能测试、安全测试、操作日志审计验证。
4. **第 6 周（灰度上线）**：1 支行 200 人灰度，配套培训物料 + 主管使用指南 + 客服 FAQ 同步交付，关键指标日报告。
5. **第 7-8 周（灰度观察）**：监控 DAU / 任务流转时长 / 通知到达率 / 客诉，收集试点反馈，决定是否放量。
6. **回滚策略**：小程序端可下线版本回退到 PC + 纸质流程（业务方原流程未拆除，作为 MVP fallback）；后端服务支持开关控制小程序入口可见性。

## Open Questions

1. **支行行长视角是否在 MVP 范围内？** 当前默认仅「客户经理 / 主管」两级，若灰度阶段支行行长强需求看团队聚合，是否本期增量？
2. **OTP 通道最终方案**：是统一走行内短信网关 OTP，还是行内员工令牌 / 行内 App 二次确认？需安合团队最终决策。
3. **收单系统接口实时性是否真的能在 5 分钟内同步？** 需收单系统方给出接口 SLA 承诺，否则商户详情「收单状态」展示规则需调整。
4. **图片附件保留期限**：跟进记录 + 完成回报图片附件保留多久？是否需自动删除策略？由数据合规团队明确。
5. **任务池可见范围**：v1 默认「同团队可见」，是否需支持主管自定义可见范围（例如指定若干客户经理）？
6. **敏感字段明文 30 秒窗口是否需可配置？** 不同支行 / 业务条线对该窗口长度的偏好可能不同，是否纳入运营配置后台？
7. **小程序入口归属**：挂在行内员工 App 子菜单 / 行内统一小程序矩阵 / 独立小程序？影响 SSO 桥接方式与发布审核路径。
